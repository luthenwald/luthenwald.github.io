Why building a ssg

The Inversion

Most static site generators ask the same question: where do you keep your content? The canonical answer is a content/ directory of markdown files, wired to HTML templates, glued together with YAML front-matter. The SSG mediates between them as a translation layer.

This one refuses the premise.

A Haskell file already speaks in two registers: comments and code. Comments are prose. Code is code. The structural boundary between them is enforced by the language itself. No additional format is needed. The file you write the program in is the file you publish.

The blog you are reading is a .hs file. This paragraph is a comment. The definitions below are code. The SSG treats them accordingly.

Two Registers, One File

The first thing the SSG does with any source file is ask: where are the comments, and where is everything else?

Ext scans line by line. A contiguous run of comment-prefixed lines, bounded above and below by blank lines (or the file boundary), becomes an RCom. Everything in the gaps between those runs becomes RCod, carrying only a line range. If you know where the prose is, you know where the code is by subtraction.

data Com = Com
   { comTxt :: Text
   , comBeg :: Int
   , comEnd :: Int
   }

data Rgn
   = RCom Com
   | RCod Int Int

RCom strips the comment prefix — -- for Haskell, # for fish — and carries the cleaned text alongside its line range. RCod records only a line range; the code is never copied into the region, only referenced by position.

Code regions emerge from the complement of comment regions:

codeGaps :: [Com] -> Int -> [Rgn]
codeGaps [] tot
   | tot > 0   = [RCod 1 tot]
   | otherwise = []
codeGaps (c:cs) tot = bef ++ gaps ++ aft
 where
   bef  = [RCod 1 (comBeg c - 1) | comBeg c > 1]
   gaps = [ RCod (comEnd a + 1) (comBeg b - 1)
          | (a, b) <- zip (c:cs) cs
          , comEnd a + 1 <= comBeg b - 1
          ]
   aft  = [RCod (comEnd (last (c:cs)) + 1) tot
          | comEnd (last (c:cs)) < tot]

Regions are sorted by start line and handed upstream. Two constructors and one subtraction: the whole epistemology of the extractor.

The Contract at the Top

The first RCom is not prose. It is a promise. It must carry exactly four keys: title, pubDate, tags, description. Met parses it with Megaparsec and validates the result immediately. A missing key or a malformed date is a build error. There are no warnings. The contract has no optional clauses.

data Met = Met
   { metTtl :: Text
   , metPub :: Text
   , metTag :: Text
   , metDsc :: Text
   }

validate :: FilePath -> Met -> Either String Met
validate pth m
   | T.null (metTtl m)          = Left $ pth ++ ": missing 'title'"
   | T.null (metPub m)          = Left $ pth ++ ": missing 'pubDate'"
   | not (validDate (metPub m)) = Left $ pth ++ ": invalid pubDate, expected yyyy-mm-dd"
   | T.null (metTag m)          = Left $ pth ++ ": missing 'tags'"
   | T.null (metDsc m)          = Left $ pth ++ ": missing 'description'"
   | otherwise                  = Right m

If validation passes, the remaining RCom regions are handed to Mrk. 1

A minimal markup

Mrk defines what prose is allowed to be. Block dispatch is keyed entirely on line prefix:

| heading, depth proportional to | count

- list item, depth proportional to - count

> callout (rendered as <blockquote>)

^N. footnote definition

@insert and @img directives, resolved later by Bld

6 or more backticks: verbatim block

anything else: paragraph

No nesting. No block elements containing other block elements. The AST is flat by design:

data Blk
   = Hdg Int [Inl] Text
   | Par [Inl]
   | Lst Int [Inl]
   | Cal [Inl]
   | Ftn Int [Inl]
   | Cod Text
   | Vrb Text
   | Raw Text
   | Ins FilePath
   | Img FilePath

data Inl
   = Txt Text
   | Lnk Text Text
   | Bld Text
   | Cde Text
   | Ref Int

Inline elements — *bold*, ` code , text, [^N]` — are parsed with Megaparsec inside each block. Block parsing is a left fold over lines, never backtracking across block boundaries.

Cod nodes are not produced by Mrk. They arrive pre-formed from Ext, each carrying {{n}} placeholders — one per source line in the code region. Their content is filled in by the next stage: Hlt.

Delegating Sight

Syntax highlighting is the one responsibility the SSG declines to own. Hlt shells out to tree-sitter highlight -H --css-classes on the original source file. Tree-sitter returns an HTML table: one <tr> per source line, each carrying the highlighted span markup for that line.

Hlt parses that table into a Map Int Text, keyed by line number. The {{n}} placeholders in each Cod block are then substituted in one pass:

subst :: Map Int Text -> Blk -> [Blk]
subst lmp (Cod txt) =
   let lns = T.lines txt
       out = [ case parsePlaceholder l of
                  Just n  -> Map.findWithDefault "" n lmp
                  Nothing -> l
             | l <- lns ]
       res = T.dropWhile (== '\n')
           $ T.dropWhileEnd (== '\n')
           $ T.intercalate "\n" out
   in  [Cod res | any (not . T.null . T.strip) out]
subst _ blk = [blk]

Tree-sitter runs on the file as a whole — it highlights every line, including the comment lines that the SSG will ultimately discard as prose. Only the line numbers referenced by Cod placeholders survive into the output.

If tree-sitter is absent or fails, Hlt returns an empty map. Placeholders become empty strings; code blocks render without highlighting. The build does not abort. 2

The Output World

After extraction, metadata, markup, and highlighting, each source file collapses into a Doc:

data Doc = Doc
   { docMet :: Met
   , docBlk :: [Blk]
   , docOut :: [Out]
   , docPth :: FilePath
   }

data Out = Out
   { outTxt :: Text
   , outLvl :: Int
   , outId  :: Text
   }

docOut is derived from the headings in docBlk and rendered as a sidebar outline.

Bld orchestrates the full pipeline: scan with Scn, process each file, sort by metPub descending, then write:

blogs/<id>.html per post, with the sidebar outline

index.html listing all posts chronologically

tags/tagcloud.html and one page per tag

feed.xml as RSS 2.0

@img references are base64-encoded into data: URIs and inlined directly. @insert references are read as raw HTML and wrapped in a container <div>. Each page carries no external asset dependencies beyond two CSS files.

Ten modules, ~650 lines, no external runtime beyond tree-sitter. This post was built by it.
